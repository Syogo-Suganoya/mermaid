01Mermaid ってなに？

Mermaid（マーメイド）は、文字で書いた「図の説明」を読んで、図を描いてくれるプログラムです。四角や矢印をマウスで並べる代わりに、「A から B へ矢印」のように文章で書きます。文章なので、あとから直すのも、変更の記録（Git）に残すのもかんたんです。

GitHub や Notion、VS Code などで、Markdown の中に ```mermaid と書くだけで図になるのは、裏でこの Mermaid が動いているからです。下の左側の文字を書きかえると、右側の図がその場で変わります。

図を準備しています…

この体験コーナーは、インターネット上で公開されている mermaid（v11.4.1）を読みこんで描いています。この資料で解説しているのは、手元のリポジトリの v12.1.0 です。

いいところ

文章だから扱いやすい

  • キーボードだけで図が作れる
  • 直した場所が Git の差分でわかる
  • 同じ書き方で、色やレイアウトだけ変えられる
描ける図

37 通りの書き始め

  • フローチャート・シーケンス図・クラス図
  • ガントチャート・円グラフ・XY チャート
  • マインドマップ・タイムライン・カンバン など

02全体の地図

Mermaid には、ふつうの Web サービスのようなサーバーやデータベースがありません。配られるのは JavaScript のファイル（mermaid.js）だけで、図はすべて見ている人のブラウザの中で作られます。

このリポジトリは、いくつかの「パッケージ」をまとめて管理するモノレポという形です。主役は packages/mermaid で、文法の読み取り（packages/parser）や、追加のレイアウト（layout-elk・layout-tidy-tree）が別のパッケージになっています。

ポイントサーバーがないので、図の中身が外に送られることはありません。そのかわり「悪い人が書いた図の説明」も見る人のブラウザで動いてしまうので、安全のしくみ（11章）がとても大事になります。

03プログラムの役割分担

本体のプログラムは packages/mermaid/src にあり、プログラムのファイルは約 834 個あります。仕事を「受付 → 進行役 → 図1枚 → 担当チーム → 道具箱」のように分けているので、直したい場所を見つけやすくなっています。

受付
mermaid.ts

外から呼ばれる窓口。run()・render()・parse() などを用意し、頼まれた仕事を順番待ちの列（キュー）に並べて1つずつ片づける。

進行役
mermaidAPI.ts

図を1枚作る段取りを全部受けもつ。下ごしらえ、設定、CSS 作り、描画、安全チェックの順に進める。

図1枚
Diagram.ts

「これは何の図か」を当て、担当チームを呼んできて、文を読ませる。

担当チーム
diagrams/<図の種類>/

図の種類ごとのフォルダ。中は同じ顔ぶれの5人組でできている（下の表）。

道具箱
rendering-util/・themes/

どの図でも使える共通の道具。箱や線の描き方、置き場所の計算、色の組み合わせ。

担当チームの5人組ファイル名の例仕事
見分け係（detector）pieDetector.ts1行目を見て「自分の担当の図か」を答える。担当なら残りのメンバーを呼ぶ方法も知っている
読み取り係（parser）pie.langium・flow.jison文法のルールに沿って文を部品に分ける
記録係（db）pieDb.ts読み取った部品を、配列やオブジェクトにためておく。「箱が5個、矢印が4本」のようなデータになる
描き係（renderer）pieRenderer.ts記録係のデータを見て SVG を描く
色係（styles）pieStyles.tsテーマの色から、その図用の CSS を作る
なぜ分けるの？新しい図を足したいときは、5人組のフォルダを1つ作って名簿（diagram-orchestration.ts）に書き足すだけで済みます。ほかの図のコードにさわらないので、うっかり壊すことが減ります。

04文字が図になるまで

Web ページに <pre class="mermaid"> と書いて Mermaid を読みこむと、ページの読みこみが終わったところで次の順に処理が進みます。

  1. 図の説明を集める

    class="mermaid" の要素をページから全部探し、中の文字を取り出す。2回描かないように data-processed という目印を付ける。

    mermaid.ts の run()

  2. 順番待ちの列に並ぶ

    図を描く作業は時間がかかるので、たくさん頼まれても混ざらないよう、キューに入れて1つずつ処理する。

    mermaid.ts の executionQueue

  3. 下ごしらえ

    改行の種類をそろえ、先頭の --- で囲まれた設定（frontmatter）や %%{init: …}%% を取り出し、%% から始まるコメントを消す。

    preprocess.ts

  4. 何の図かを当てる

    1行目の言葉を見分け係に順に見せて、最初に「はい」と答えた図に決める（5章）。

    diagram-api/detectType.ts

  5. 担当チームを呼ぶ・文を読む

    担当チームのファイルをその場で読みこみ（遅延読みこみ）、読み取り係が文を部品に分けて記録係にためる（6章）。

    Diagram.ts の fromText()

  6. CSS を作る

    テーマの色と、図の中で classDef などで決めた色から CSS を作り、SVG の先頭に入れる（9章）。

    mermaidAPI.ts の createUserStyles()

  7. 置き場所を決めて描く

    描き係が、記録係のデータから箱や線の位置を決めて SVG を描く（7・8章）。

    各図の renderer の draw()

  8. 読み上げ用の情報を足す

    目の不自由な人の読み上げソフトのために、accTitle・accDescr で書いたタイトルや説明を SVG に付ける。

    accessibility.ts

  9. 安全にしてページに入れる

    SVG を文字列にし、危ないスクリプトが混ざっていないかを DOMPurify で調べて取り除く。最後に元の要素の中身を SVG に入れかえる（11章）。

    mermaidAPI.ts・mermaid.ts

書きまちがえたときは読み取りで失敗すると、代わりに「error」という特別な図（爆弾のマークとエラー文）を描きます。エラーの内容は図にも表示され、呼び出した側には例外として知らせます。

05何の図かを当てるしくみ

図の種類は、先頭の言葉で決まります。flowchart ならフローチャート、sequenceDiagram ならシーケンス図です。Mermaid は名簿に書かれた順に見分け係へ文を見せ、最初に当たった図に決めます。下は flowchart LR … を見分けるときの順番です。

flowchart-elkmindmaparchitectureagentflowc4kanbanclassDiagramerganttinfopierequirementsequenceswimlaneflowchart-v2 ✓timelinegitGraphstateDiagramjourneyquadrantChartsankeypacketxychartblockeventmodelingtreeViewradarishikawatreemaprailroadrailroadEbnfrailroadAbnfrailroadPegvennwardleycynefinusecase

見分け係は、ほとんどが「正規表現」という文字のパターン1つでできています。たとえばフローチャートの見分け係は /^\s*(graph|flowchart)/、つまり「空白のあとに graph か flowchart で始まるか」を調べるだけです。

順番が大事

flowchart-elk は flowchart より先

flowchart-elk という書き始めは、フローチャートのパターン（flowchart で始まる）にも当てはまってしまいます。そこで名簿では flowchart-elk を先に並べ、先に当たるようにしています。

遅延読みこみ

使う図だけ読みこむ

はじめに読みこむのは見分け係だけです。図が決まってから、その図の読み取り係・記録係・描き係を import() で取りに行きます。37 種類ぶん全部を最初に読むより、ずっと速く表示できます。

軽量版 tinyCDN 向けの mermaid.tiny では、大きな部品が要るマインドマップ・アーキテクチャ図・flowchart-elk の見分け係を名簿から外し、ファイルを小さくしています。

06文を読み解くしくみ

国語で文を「主語・述語」に分けるように、Mermaid も文法のルールを使って文を部品に分けます。この係をパーサーと呼びます。たとえば次の1行は、こう分けられます。

Aノードの名前
[注文]四角い形と文字
-->矢印
Bノードの名前
{在庫ある?}ひし形と文字

パーサーを手で書くのは大変なので、Mermaid では文法のルールを書いたファイルから、パーサーのプログラムを自動で作っています。作り方は3通りあります。

Jison

19 種類の図

昔からある方式。.jison ファイルに単語の区切り方と文法を書く。ビルドのときに JavaScript に変換される。読みながら記録係の関数を直接呼ぶ。

例：フローチャート・シーケンス図・ガントチャート

Langium

12 種類の図

新しい図で使う方式。.langium に文法を書くと、文の構造を木の形（AST）にしてくれる。記録係はその木を読んでデータにする。別パッケージ packages/parser にまとまっている。

例：円グラフ・Git グラフ・アーキテクチャ図

Chevrotain

1 種類の図

文法をファイルではなく TypeScript のプログラムとして書く方式。単語の区切り（lexer）と文法（parser）と読み取り結果の変換（visitor）を自分で組み立てる。

例：ユースケース図

記録係にためるどの方式でも、最後は記録係（db）に「ノードの一覧」「矢印の一覧」などがたまります。描き係はパーサーのことを知らなくても、記録係のデータだけを見て描けます。

07置き場所を決めるしくみ

部品がわかっても、どこに置くかはまだ決まっていません。箱どうしが重ならず、線ができるだけ交差しない位置を探す計算をレイアウトと呼びます。

箱と線の図は、みんな同じ道具で並べる

フローチャート・状態遷移図・クラス図・ER 図・要求図・マインドマップ・エージェントフロー図・ユースケース図の 8 種類は、記録係が getData() で共通の形（LayoutData：ノードの配列と線の配列）にデータを渡し、同じ道具で描きます。道具は4つの手順で動きます。

  1. 下準備（prepare）

    レイアウトの計算に使う形にデータを組みかえる。

  2. 測る（measure）

    文字の入った箱をいったん見えないところに描いて、本当の幅と高さを測る。文字の大きさはフォントで変わるので、描いてみないとわからない。

  3. 置き場所を計算する（layout）

    dagre や ELK などのレイアウトの道具に、箱の大きさとつながりを渡して座標を計算してもらう。

  4. 描く（paint）

    計算した座標に箱を動かし、線を引き、グループの枠を描く。

dagre

いつもはこれ

段に分けて並べる階層型。何も指定しないときに使われる。

elk

大きな図に強い

Eclipse の ELK を使う。線をまっすぐ曲げるなど、細かい調整ができる。

cose-bilkent

ばねで広げる

箱どうしをばねでつないだように引っぱり合わせて広げる。マインドマップで使う。

swimlane

レーンに分ける

担当ごとの帯（レーン）に箱を並べる。スイムレーン図で使う。

tidy-tree

木の形

別パッケージ。親から子へ枝分かれする形にきれいに並べる。

ガントチャートや円グラフのように並べ方が決まっている図は、この道具を使わず、描き係が D3 というライブラリで直接 SVG を組み立てます。

差しかえられるレイアウトは layout: elk のように設定で選べます。道具を名簿（registerLayoutLoaders）に登録するしくみなので、外のパッケージから新しいレイアウトを足すこともできます。

08形と線を描くしくみ

置き場所が決まったら、SVG という形式で絵を描きます。SVG は「(10, 20) から (100, 20) まで線」のように数字で絵を表すので、拡大してもぼやけません。

矢印がふちでぴたりと止まる理由

線の終わりは、箱の真ん中ではなく形のふちにします。四角・円・多角形それぞれについて、線と形がぶつかる点を計算する関数（intersect/）が用意されています。ひし形のような多角形は、辺を1本ずつ調べて交わる点を探します。

文字

折り返しと太字

文字は SVG の text か、HTML を入れられる foreignObject で描く。"`**太字**`" のような Markdown も使える。

数式

KaTeX

$$x^2$$ と書くと、KaTeX で数式にしてから入れる。

アイコン

アイコンパック

registerIconPacks で登録したアイコンを、icon:logos:aws のように名前で使える。

09色と見た目のしくみ

同じ文字から、色の組み合わせ（テーマ）を変えた図を作れます。テーマは 11 種類あります。

basedarkdefaultforestneutralneoneo-darkreduxredux-darkredux-colorredux-dark-color

数色を決めれば、残りは計算

テーマは primaryColor（メインの色）など少しの色を決めるだけで、線の色・文字の色・背景の色などは、明るさや色合いを少しずらす計算で自動で作られます（khroma というライブラリを使用）。だから themeVariables で1色変えるだけで、全体がなじむ色になります。

見た目（look）も選べる

classic（いつもの）、handDrawn（手描き風）、neo（新しいデザイン）から選べます。手描き風は roughjs で線をわざとゆらして描きます。

設定は重ねて決まる

設定は、下から順に上書きされていきます。あとから書いたものが勝つしくみです。

図の中の設定frontmatter（--- の中の config:）と %%{init: …}%%
サイトの設定ページを作った人が mermaid.initialize({ … }) で決めたもの
はじめからの設定config.schema.yaml に書かれた既定値（defaultConfig）
図の中からは変えられない設定securityLevel や maxTextSize など、安全に関わる 6 個の設定は「secure」という名簿に入っていて、図の中の設定では上書きできません（11章）。

11ミスや悪用を防ぐしくみ

世界中の人がコードを直すオープンソースなので、「人が気をつける」だけに頼らず、プログラムで自動的に止めるしくみがたくさんあります。守っているものは、大きく分けてコードと図を見る人の2つです。

コードのミスを、取りこむ前に止める

Vitest

部品ごとのテスト（316 ファイル）

ソースの隣に *.spec.ts を置き、関数に入力を与えて期待どおりの出力になるかを自動で確かめる。

Playwright + Argos

お手本の図（1242 枚）

e2e/diagrams/ の .mmd ファイルを本物のブラウザで描いて撮影し、前の画像と1枚ずつ見比べる。見た目が少しでも変わると知らせる。

ESLint・Prettier・cspell

書き方のチェック

よくあるミスの書き方、整形のばらつき、英単語のつづりまちがいを見つける。

GitHub Actions

自動チェック

プルリクエストのたびに、テスト・lint・型チェック・設定の型とスキーマのずれ・ファイルどうしの循環参照・ドキュメントの生成もれを調べる。

図を見る人を守る

しくみ防ぐものやっていること
DOMPurify図の文字にスクリプトを混ぜる攻撃（XSS）できあがった SVG と、ラベルの文字を調べ、<script> や onclick などの危ない部分を取り除く
securityLevelクリックで勝手にプログラムが動くことstrict（既定）では click で関数を呼ぶ書き方を無効にする。sandbox では図を iframe という別の小部屋に閉じこめる
secure な設定図の中から安全の設定をゆるめることfrontmatter や %%{init}%% に securityLevel などが書かれていたら消す
設定の掃除設定に危ない値を混ぜる攻撃図の中の設定で、< > を含む文字や __proto__ のような名前を消す
大きさの上限巨大な図でブラウザが固まること文字数は 50,000 文字（maxTextSize）、線は 500 本（maxEdges）まで

e2e テストにも xss.spec.js などの攻撃を試すテストがあり、過去に見つかった弱点が再び起きないかを毎回確かめています。
